# ИТ Школа · Партнёры

Первый работающий срез CRM: React + TypeScript, FastAPI + SQLAlchemy, PostgreSQL как целевая БД, Keycloak для OIDC. Для быстрого локального знакомства предусмотрен явный режим разработки с SQLite и переключением синтетических пользователей.

Это **не полная реализация ТЗ и не готовый production-релиз**. Образовательные организации, контакты и действия в seed вымышлены; имена пользователей обозначают тестовые персоны. Реальные LMS/сайт не подключены, персональные данные заказчика не загружаются.

## Что входит в этот срез

- Обзор с рассчитанными по доступным данным показателями; реестр и карточка взаимодействия, фильтры и справочники.
- Создание взаимодействия; допустимые переходы базового процесса, комментарии, история, смена ответственного руководителем в своей команде.
- Проверка доступа на сервере, защита от потерянного обновления через revision, ключи идемпотентности для изменяющих операций.
- Исторический отчёт «состояние на дату» с историческим ответственным/статусом и текущими правами просмотра; ограниченный синхронный расчёт на небольших данных.
- Скачивание **JSON**. XLS, XLSX, PDF, PNG, импорт Excel, вложения, редактор/миграция workflow, фоновые отчёты и учебная статистика в этом срезе не реализованы; подмены форматов нет.
- Открытое описание API в Swagger UI; отдельные live/ready endpoints.

50 одновременных пользователей, 10 одновременно строящихся отчётов и нормативное соответствие ещё не подтверждены. Модульный монолит подготовлен к дальнейшему расширению; отдельный worker в текущем compose намеренно отсутствует, потому что фоновых задач пока нет. Полный объём и критерии приёмки находятся в соседних проектных документах `01-technical-specification.md`, `02-development-plan.md`, `03-acceptance-scenarios.md`.

Подробная версия анализа требований, технической спецификации, плана, сценариев приёмки, workflow и отчётного фикстура лежит в [`docs/planning/`](docs/planning/). Проверяемые инварианты находятся в [`docs/checks/`](docs/checks/), а контракт первого среза — в [`docs/implementation-contract.md`](docs/implementation-contract.md).

## Быстрый локальный запуск: SQLite + явный demo mode

Нужны Python 3.12+ (при разработке доступен Python 3.13), Node.js 24 и pnpm 11.19.0. Команды запускайте из корня этого репозитория `rtk-crm`. Виртуальная среда и SQLite-файл остаются в `backend/` и исключены из Git.

### Windows / PowerShell — терминал 1, API

```powershell
Set-Location backend
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:APP_ENV = 'development'
$env:AUTH_MODE = 'demo'
$env:DATABASE_URL = 'sqlite:///./rtk-demo.db'
.\.venv\Scripts\python.exe -m app.seed --seed-demo
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### Linux / macOS — терминал 1, API

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
export APP_ENV=development
export AUTH_MODE=demo
export DATABASE_URL=sqlite:///./rtk-demo.db
.venv/bin/python -m app.seed --seed-demo
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### Терминал 2, интерфейс — обе платформы

Откройте второй терминал в корне `rtk-crm`:

```text
cd frontend
npm install --global pnpm@11.19.0
pnpm install --frozen-lockfile
pnpm dev --host 127.0.0.1
```

Откройте [интерфейс](http://localhost:5173). В этом режиме выбор пользователя в интерфейсе передаёт явный заголовок `X-Demo-User`; это демонстрационный обход реального входа, разрешённый **только** сочетанием `AUTH_MODE=demo` и `APP_ENV=development`. Внешнему пользователю такой стенд не публикуют. Сервер без указания пользователя не должен молча выбирать менеджера.

Swagger API доступен на [localhost:8000/docs](http://localhost:8000/docs), состояние БД — [localhost:8000/health/ready](http://localhost:8000/health/ready). Для прямого обращения к защищённому API используйте `X-Demo-User: manager-a` или другой явный ID из таблицы ниже. Остановка сервера — Ctrl+C; файл SQLite сохраняется. `--seed-demo` создаёт схему и идемпотентно добавляет синтетические записи, обычный запуск API их не добавляет.

## Docker Compose: PostgreSQL + настоящий OIDC + nginx

Нужны запущенный Docker Engine / Docker Desktop с Linux-контейнерами и Compose v2 с `--wait`. Конфигурация ниже — локальный тестовый стенд с реальной проверкой JWT, **а не production-конфигурация**. HTTP и `Keycloak start-dev` допустимы здесь только для локального знакомства. Порты опубликованы на `127.0.0.1`; PostgreSQL и API доступны только внутри compose-сети.

### 1. Создать локальные параметры

PowerShell:

```powershell
Copy-Item .env.example .env
```

Linux/macOS:

```bash
cp .env.example .env
```

Откройте `.env` и задайте пароли **до первого старта**. Значения-примеры имеют явный префикс `dev_only`; это не production-секреты. Для `CRM_DB_PASSWORD` данный DSN ожидает URL-safe символы `[A-Za-z0-9_-]`; для произвольного пароля нужна корректная URL-кодировка при сборке URL. `.env` исключён из Git. Не публикуйте вывод `docker compose config`: он может содержать подставленные значения; для проверки используйте `--quiet`.

### 2. Собрать и запустить пустую CRM

Из корня `rtk-crm`, одинаково на обеих платформах:

```text
docker compose config --quiet
docker compose up --build --detach --wait --wait-timeout 240
docker compose ps
```

PostgreSQL создаёт отдельные БД/роли `rtk_crm` и `keycloak` на одном локальном сервере. API выполняет только `python -m app.seed --init-db`; в первом срезе это создание схемы, а не промышленный набор версионированных миграций. Обычный старт не заселяет CRM демонстрационными данными.

### 3. Явно добавить синтетические записи для показа

```text
docker compose exec api python -m app.seed --seed-demo
```

Теперь откройте [CRM](http://localhost:3000). Вход перенаправляет в [Keycloak](http://localhost:8080); выберите одну из четырёх тестовых учётных записей. Пока seed не выполнен, успешного входа в Keycloak недостаточно: соответствующая локальная запись пользователя CRM отсутствует.

| Логин / локальный ID | Роль и демонстрационная область | Переменная пароля в `.env` | Ожидаемый JWT `sub` |
|---|---|---|---|
| `manager-a` | Менеджер Анна; собственные взаимодействия | `DEMO_MANAGER_A_PASSWORD` | `11111111-1111-4111-8111-111111111111` |
| `manager-b` | Менеджер Михаил; собственные взаимодействия | `DEMO_MANAGER_B_PASSWORD` | `22222222-2222-4222-8222-222222222222` |
| `supervisor` | Руководитель Елена; команда `north` | `DEMO_SUPERVISOR_PASSWORD` | `33333333-3333-4333-8333-333333333333` |
| `administrator` | Администратор; без автоматического чтения всех бизнес-данных | `DEMO_ADMINISTRATOR_PASSWORD` | `44444444-4444-4444-8444-444444444444` |

Тестовые пользователи импортируются в realm при первоначальной инициализации Keycloak; их пароли берутся из окружения. Bootstrap-администратор Keycloak (`KEYCLOAK_ADMIN_USER`) — отдельная учётная запись для консоли управления, не CRM-пользователь `administrator`.

### Согласованные OIDC-параметры

| Параметр | Значение |
|---|---|
| Realm | `rtk-crm` |
| Публичный browser client | `rtk-crm-web` |
| Flow | Authorization Code + PKCE S256; password grant отключён |
| Issuer | `http://localhost:8080/realms/rtk-crm` |
| Обязательная audience API | `rtk-crm-api` |
| Роли токена | `realm_access.roles`: `manager`, `supervisor`, `administrator` |
| JWKS для API внутри Docker | `http://keycloak:8080/realms/rtk-crm/protocol/openid-connect/certs` |
| Browser redirects/origins | Только `http://localhost:3000` и `http://localhost:5173` с разрешёнными локальными путями |

Внутренний адрес JWKS используется только для получения ключей. Проверяемый `iss` остаётся публичным адресом; его нельзя заменить на `http://keycloak:8080` ради сетевого удобства. API проверяет подпись, алгоритм, срок, issuer, audience, соответствие локального пользователя и роль. Токен не заменяет предметную проверку доступа.

Swagger через nginx: [localhost:3000/docs](http://localhost:3000/docs); health: [localhost:3000/health/ready](http://localhost:3000/health/ready). Swagger сам по себе не отменяет аутентификацию: для защищённых вызовов требуется корректный access token.

### Повторный запуск и диагностика

```text
docker compose logs --tail 100 api keycloak
docker compose stop
docker compose start
```

Данные сохраняются в именованном томе `postgres-data`. `docker compose down` останавливает/удаляет контейнеры и сеть, сохраняя том. Не используйте удаление томов как обычный способ перезапуска: оно уничтожает и CRM, и Keycloak.

Стартовый импорт пропускает существующий realm: изменения JSON-файла и паролей `.env` не переписывают автоматически уже созданные учётные записи. Скрипт создания БД тоже выполняется только на пустом томе. Менять существующие пароли нужно штатно в соответствующем сервисе и затем согласованно обновлять конфигурацию; файл импорта не является полноценной резервной копией.

Открывайте стенд именно как `localhost`, а не IP-адрес компьютера или `127.0.0.1` в адресной строке: redirects и issuer настроены на `localhost`. Смена hostname/портов требует согласованно обновить публичный URL Keycloak, issuer, frontend origins и realm redirect URIs; одной переменной недостаточно.

## Проверки разработки

В виртуальной среде backend нужны тестовые зависимости `pytest` и `httpx`:

PowerShell, из `backend/`:

```powershell
.\.venv\Scripts\python.exe -m pip install pytest httpx
.\.venv\Scripts\python.exe -m pytest -q
```

Linux/macOS, из `backend/`:

```bash
.venv/bin/python -m pip install pytest httpx
.venv/bin/python -m pytest -q
```

Из `frontend/`, обе платформы:

```text
pnpm install --frozen-lockfile
pnpm build
```

Важные ручные сценарии: менеджеры видят разные записи; прямой запрос чужой карточки запрещён; руководитель меняет ответственного; недопустимый переход/устаревшая revision/повтор с другим payload не затирают данные; отчёт на прошлую дату использует прошлое состояние и текущую область доступа; JSON скачивается и совпадает с таблицей. Проверка локального demo mode не доказывает работоспособность реального browser OIDC.

Для проверки compose нужны отдельный запуск контейнеров и реальный браузерный вход всех ролей. На среде первоначальной подготовки Docker отсутствовал, поэтому **успешный контейнерный прогон и сквозной вход Keycloak здесь не заявляются**. Структурная проверка YAML/JSON не подтверждает доступность образов, readiness, realm import или сетевые взаимодействия. Фактические выполненные проверки фиксируются отдельно с результатом и условиями.

## Перед эксплуатацией

Этот стенд нельзя объявить эксплуатационным, поменяв только `APP_ENV`. Для внедрения нужны HTTPS и действительные домены, production-режим/управление Keycloak, убранные тестовые пользователи и импорт, секреты вне репозитория, отдельные минимальные права БД и проверенные миграции. Версии образов следует зафиксировать по digest после успешного прогона и проверки обновлений: текущие version-tags без digest ещё могут изменяться.

Также необходимы согласованные правила доступа/данных, реальные API, очередь и workers для длительных задач, все обязательные форматы, обработка файлов, мониторинг, резервирование и проверка восстановления, нагрузочная приёмка и организационные решения ИБ. Случайные bootstrap-пароли и realm JSON не заменяют эти работы. Нормативное соответствие данным срезом не подтверждается.

Для реализации контейнерного стенда использованы официальные сведения: [Keycloak container/start-dev/health](https://www.keycloak.org/server/containers), [стартовый импорт realm и переменные окружения](https://www.keycloak.org/server/importExport), [фиксированный hostname](https://www.keycloak.org/server/hostname). Версия Keycloak `26.7.4` выбрана по [официальной странице загрузок](https://www.keycloak.org/downloads) на момент подготовки; поддержка и обновления проверяются перед эксплуатационным выпуском.
