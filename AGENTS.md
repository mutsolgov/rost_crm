# Правила и принципы работы агентов в проекте rost_crm

Этот документ является обязательной инструкцией для всех AI-агентов (архитектор, разработчик, ревьюер, тестировщик), работающих в репозитории проекта "ИТ Школа Ростелекома — CRM" (`rost_crm`).

---

## 1. Философия Ponytail (Защита от оверинжиниринга и избыточного кода)

Ты — опытный старший разработчик (lazy senior developer). Твоя цель — решить задачу максимально лаконично, надежно и эффективно. **Лучший код — это код, который не пришлось писать.**

### Принцип «Лестницы» (The Ladder)
Перед тем как писать хоть одну строчку кода, остановись на первой ступени, которая закрывает задачу:
1. **Нужно ли это вообще создавать?** Спекулятивные требования «на будущее» отбрасываются (YAGNI).
2. **Уже есть в нашей кодовой базе?** Найди и переиспользуй хелпер, модель, утилиту или хук, который уже написан (`app/services.py`, `app/models.py`, `src/ui.tsx`, `src/hooks.ts`). Не пиши копию в соседнем файле.
3. **Стандартная библиотека Python/JS делает это?** Используй возможности `stdlib` (например, `functools.lru_cache`, `collections.Counter`, `hashlib`, `pathlib`, `crypto.randomUUID()`).
4. **Нативная фича платформы закрывает вопрос?** Используй нативные возможности: `<input type="date">` вместо тяжелых календарных библиотек, `<input type="file">` вместо сторонних аплоадеров, CSS вместо скриптов, DB constraints вместо сложной логики приложения.
5. **Уже установленная зависимость решает задачу?** Используй то, что уже есть в `requirements.txt` / `package.json`. Не добавляй новые npm/pip пакеты, если задачу можно решить 5–10 строками стандартного кода.
6. **Можно сделать в одну строку?** Сделай в одну строку.
7. **Только если предыдущее не подошло:** пиши минимально необходимый рабочий код.

### Правила минимизации
- **Никаких абстракций без запроса:** никаких интерфейсов с одной реализацией, никаких фабрик для одного класса, никаких универсальных шин событий, если достаточно прямого вызова функции.
- **Удаление важнее добавления:** если можно решить баг удалением лишнего слоя — удаляй.
- **Минимальный diff:** побеждает наименьший рабочий diff, затрагивающий наименьшее число файлов.
- **Починка первопричины (Root Cause):** не ставь «заплатку» в месте проявления симптома. Найди общую функцию-источник и исправь её один раз для всех вызывающих мест.

## 2. Защита от галлюцинаций и потери контекста (Антигаллюцинаторный протокол)

### 2.1. Иерархия источников правды
Никогда не придумывай архитектуру, модели данных или статусы процессов заново. Все решения должны строго опираться на зафиксированные документы:
1. Исходное ТЗ заказчика (`PDF`)
2. Контракт реализации (`docs/implementation-contract.md`)
3. Архитектурные решения (`docs/planning/adr/`)
4. Спецификация (`docs/planning/01-technical-specification.md`)
5. Анализ разрывов (`docs/planning/07-gap-analysis.md`)
6. Анализ дизайн-системы (`docs/planning/08-ui-design-system-analysis.md`)
7. Эталонные данные (`04-base-workflow.json`, `05-report-fixture.json`)
8. План задач B01–B40 (`02-development-plan.md`) и сценарии AC01–AC30 (`03-acceptance-scenarios.md`)

### 2.2. Запрет на самодеятельность в контрактах API и БД
- Все эндпоинты имеют строгий префикс `/api/v1/`.
- Все ошибки возвращаются в едином формате: `{error: {code, message, request_id, details}}`.
- Статусы жизненного цикла строго соответствуют 13 рабочим + 2 терминальным состояниям из `04-base-workflow.json`. Никаких выдуманных или переименованных статусов!
- Изменяющие операции обязаны требовать заголовок `Idempotency-Key` (максимум 200 символов) и проверять `expected_revision` через CAS update.

### 2.3. Принцип атомарности задач (Не трогать не относящийся код)
- Работай строго в рамках одной поставленной задачи (B0X / AC0Y).
- Запрещено «заодно» форматировать, рефакторить или переписывать соседние работающие модули, если задача этого прямо не требует.
- Не удаляй существующие комментарии, докстринги и отладочные проверки.

## 3. Инварианты безопасности (152-ФЗ, ФСТЭК №117)

Никогда не упрощай и не убирай:
1. **Проверку области доступа (Scope):**
   - Менеджер видит ТОЛЬКО свои взаимодействия (`Interaction.owner_id == user.id`).
   - Руководитель видит ТОЛЬКО свою команду (`Interaction.team_id == user.team_id`).
   - Администратор не имеет неявного доступа к чужим бизнес-данным.
   - Попытка прямого запроса чужого ID возвращает `404 Not Found` (не раскрывать факт существования записи).
2. **Токены аутентификации:**
   - Токены JWT хранятся ТОЛЬКО в оперативной памяти (in-memory).
   - Запрещено сохранять токены сессии в `localStorage` или `sessionStorage`!
3. **Проверку файлов:**
   - Все загружаемые файлы проверяются по допустимым расширениям (10 форматов ТЗ: `png, jpeg, pdf, zip, gzip, rar, doc, docx, xls, xlsx`) и размеру (до 25 МБ).
   - Скачивание файлов строго через эндпоинт с авторизацией и проверкой прав на карточку. Запрещены прямые публичные ссылки на файлы.

## 4. Стандарты UI / UX (Дизайн-система Ростелекома Gen2)

1. **Цветовая палитра темы Rostelecom Light:**
   - Основной бренд: фиолетовый `#7700FF` / `#6C00E0`.
   - Акцент: оранжевый `#FF4F12` / `#FF6A13`.
   - Рабочий фон: нейтральный светлый `#F4F5F8`.
   - Карточки: `#FFFFFF` с мягкими тенями.
   - Текст: высококонтрастный `#101828` (контрастность > 10:1).
2. **Отзывчивость без перезагрузки:**
   - Любые изменения статусов, добавление комментариев или смена фильтров не должны перезагружать страницу браузера (SPA).
   - При ошибке валидации формы введённый пользователем текст не должен сбрасываться.

## 5. Доступные специализированные скиллы агента

В репозитории подключены скиллы в каталоге `.agents/skills/`:
- `ponytail`: включение режима минимализма и лаконичности кода на любой задаче.
- `ponytail-review`: проведение ревью предложенного кода на предмет оверинжиниринга и лишних строк.
- `ponytail-audit`: сканирование всей кодовой базы на предмет мертвого кода, дубликатов и раздутых абстракций.
- `ponytail-debt`: учет и ревизия меток `ponytail:` временных упрощений.

## 6. Чек-лист завершения любой задачи (Definition of Done)

Задача считается выполненной только если:
1. Выполнен конкретный критерий приёмки AC0Y из `03-acceptance-scenarios.md`.
2. Все существующие тесты `backend/tests/test_working_slice.py` проходят без ошибок.
3. Добавлен необходимый минимальный тест для новой функциональности.
4. Документация в OpenAPI / Swagger UI и соответствующие ADR обновлены.
