## 1. Введение и нормативно-правовая база

Настоящий документ устанавливает исчерпывающую матрицу соответствия подсистем и программного кода CRM-системы «ИТ Школа Ростелекома — CRM» (`rost_crm`) требованиям законодательства Российской Федерации и нормативно-методических документов регуляторов в области информационной безопасности и защиты персональных данных (ПДн):

1. **Федеральный закон от 27.07.2006 № 152-ФЗ «О персональных данных»** (статьи 5, 6, 7, 9, 18.1, 19, 21).
2. **Федеральный закон от 27.07.2006 № 149-ФЗ «Об информации, информационных технологиях и о защите информации»** (статьи 13, 16).
3. **Приказ ФСТЭК России от 18.02.2013 № 21** «Об утверждении Состава и содержания организационных и технических мер по обеспечению безопасности персональных данных при их обработке в информационных системах персональных данных» (требования к уровням защищенности УЗ-3 и УЗ-2).
4. **Приказ ФСТЭК России № 117** «Об утверждении Требований о защите информации, не составляющей государственную тайну, содержащейся в государственных информационных системах».
5. **Приказ Роскомнадзора от 05.09.2013 № 996** «Об утверждении требований и методов по обезличиванию персональных данных».

### 1.1. Категории субъектов и обрабатываемых данных
В информационной системе `rost_crm` обрабатываются персональные данные следующих субъектов:
- **Работники оператора (ПАО «Ростелеком»):** ФИО, корпоративный логин, адрес корпоративной электронной почты, идентификатор подразделения/команды (`team_id`), назначенная роль (`manager`, `supervisor`, `administrator`).
- **Представители образовательных организаций (вузов-партнеров):** ФИО контактных лиц (`full_name`), должность (`position`), рабочий телефон (`phone`), рабочий адрес электронной почты (`email`), история служебного взаимодействия и документы партнерства.

Категория обрабатываемых персональных данных: **Иные категории персональных данных** (без специальной и биометрической категорий).  
Тип актуальных угроз: **Угрозы 3-го типа** (угрозы, не связанные с наличием недокументированных (декларированных) возможностей в системном и прикладном ПО).  
Необходимый уровень защищенности: **УЗ-3** (с превентивным запасом прочности по мерам **УЗ-2** для распределенных веб-систем).

## 3. Детальный разбор ключевых защитных механизмов в исходном коде

### 3.1. Защита от IDOR и сокрытие факта существования записей (Scope)
В соответствии со ст. 7 152-ФЗ и мерой ФСТЭК **УПД.3**, операторы и иные лица, получившие доступ к персональным данным, обязаны не раскрывать третьим лицам и не распространять персональные данные без согласия субъекта.

В REST API типовой ошибкой является возврат кода `403 Forbidden` при обращении к чужой записи. Код 403 подтверждает атакующему, что запись с данным идентификатором существует в базе данных, что облегчает направленный сбор персональных данных методом перебора (enumeration).

В `rost_crm` реализован строгий фильтр области доступа `scope_clause`:
- **Менеджер:** `Interaction.owner_id == user.id` (видит исключительно свои закрепленные карточки).
- **Руководитель:** `Interaction.team_id == user.team_id` (видит только карточки менеджеров своей территориальной команды).
- **Администратор:** доступ к бизнес-карточкам определяется явным делегированием прав (`OrganizationAccess.read_all == True`), административная роль не дает неявного бесконтрольного чтения чужих персональных данных.

Кодовая реализация в `backend/app/services.py`:
```python
# backend/app/services.py:43-56
def scope_clause(user):
    granted = select(OrganizationAccess.organization_id).where(
        OrganizationAccess.user_id == user.id, OrganizationAccess.read_all.is_(True))
    own = Interaction.owner_id == user.id if user.role == "manager" else false()
    team = ((Interaction.team_id == user.team_id) if user.role == "supervisor" and user.team_id
            else false())
    return or_(own, team, Interaction.organization_id.in_(granted))


def scoped_interaction(db, user, interaction_id):
    interaction = db.scalar(select(Interaction).where(Interaction.id == interaction_id, scope_clause(user)))
    if not interaction:
        raise APIError("NOT_FOUND", "Взаимодействие не найдено.", 404)
    return interaction
```

Аналогичный принцип применен при запросе файлов вложений в `backend/app/files.py`:
```python
# backend/app/files.py:151-163
def get_attachment_or_404(db: Session, user: User, interaction_id: str, attachment_id: str) -> Attachment:
    item = scoped_interaction(db, user, interaction_id)
    attachment = db.scalar(
        select(Attachment).where(
            Attachment.id == attachment_id,
            Attachment.interaction_id == item.id,
        )
    )
    if not attachment or not Path(attachment.file_path).is_file():
        raise APIError("NOT_FOUND", "Вложение не найдено.", 404)
    return attachment
```
*Результат:* При любой попытке несанкционированного доступа возвращается единообразный ответ `HTTP 404 Not Found`, маскирующий существование записей и предотвращающий утечку данных.

### 3.2. Архитектура In-Memory JWT сессий (Защита от XSS и компрометации токенов)
В соответствии с требованиями мер ФСТЭК **ИАФ.3**, **ИАФ.6** и **ОДТ.5**, аутентификационная информация субъектов должна быть защищена от извлечения вредоносными скриптами. 

Хранение токенов в `localStorage` или `sessionStorage` браузера уязвимо к атакам межсайтового скриптинга (XSS): любой вредоносный JavaScript в контексте домена имеет беспрепятственный доступ к данным хранилищам.

В `rost_crm` токены аутентификации Keycloak удерживаются **исключительно в оперативной памяти** работающего приложения:
- Используется React `useRef` для сохранения экземпляра Keycloak клиента (`keycloak.current`).
- Экземпляр клиента держит полученный по PKCE S256 JWT-токен в закрытом поле оперативной памяти JavaScript runtime.
- Токен никогда не сериализуется в `localStorage`, `sessionStorage` или незащищенные `cookies`.
- При закрытии вкладки или перезагрузке страницы оперативная память очищается операционной системой.

Кодовая реализация в `frontend/src/auth.tsx`:
```typescript
// frontend/src/auth.tsx:31, 50, 78-83
export function AuthProvider({ children }: { children: ReactNode }) {
  // ...
  const keycloak = useRef<Keycloak | null>(null);

  // ...
  const client = new Keycloak({
    url: received.oidc.url, realm: received.oidc.realm, clientId: received.oidc.client_id,
  });
  keycloak.current = client;

  // ...
  const api = useMemo(() => new ApiClient(async (): Promise<Record<string, string>> => {
    // ...
    const client = keycloak.current;
    if (!client?.authenticated) throw new ApiError('Требуется вход через Keycloak.', 'AUTH_REQUIRED', 401);
    try { await client.updateToken(30); }
    catch { throw new ApiError('Не удалось обновить сессию. Войдите повторно.', 'SESSION_EXPIRED', 401); }
    return { Authorization: 'Bearer ' + client.token };
  }), [config?.auth_mode, demoUserId, oidcReady]);
```

### 3.3. Безопасное изолированное файловое хранилище
В соответствии со ст. 19 152-ФЗ и мерами ФСТЭК **ЗВК.1**, **АВЗ.1**, **ОЦЛ.1**, подсистема загрузки файлов содержит многоуровневую фильтрацию:

1. **Белый список расширений (Whitelist):** Разрешены только 10 форматов ТЗ: `png, jpeg, jpg, pdf, zip, gzip, gz, rar, doc, docx, xls, xlsx`.
2. **Сигнатурная проверка Magic Bytes:** Сервер валидирует первые байты содержимого файла, проверяя соответствие реального типа данных расширению:
   - PNG: `\x89PNG\r\n\x1a\n`
   - JPEG: `\xff\xd8\xff`
   - PDF: `%PDF-`
   - ZIP/DOCX/XLSX: `PK\x03\x04`
   - GZIP: `\x1f\x8b`
   - RAR: `Rar!\x1a\x07`
   - DOC/XLS (OLE2): `\xd0\xcf\x11\xe0\xa1\xb1\x1a\xe1`
3. **Блокировка опасных исполняемых сигнатур:** Файлы, содержащие исполняемые заголовки Windows PE (`MZ`), Linux ELF (`\x7fELF`), Unix-скрипты (`#!`), PHP (`<?php`), HTML/JS (`<script`), Java/Mach-O (`\xca\xfe\xba\xbe`), немедленно отклоняются со статусом `422 FILE_TYPE_NOT_ALLOWED`.
4. **Защита от Path Traversal и санитизация:** Имена файлов очищаются через `PurePath(filename).name`, удаляются символы `\x00`, блокируются ссылки `.` и `..`.
5. **Изоляция на файловой системе:** Файлы сохраняются в каталог `storage/attachments/{interaction_id}/` под случайно сгенерированным UUID (`uuid4().hex.ext`), предотвращая перезапись и прямой доступ через URL.
6. **Криптографический контроль целостности:** При загрузке вычисляется контрольная сумма $SHA\text{-}256$, которая фиксируется в БД и аудит-логе.
7. **Лимит размера:** Объем загружаемого файла жестко ограничен $25\text{ МБ}$ ($26\,214\,400$ байт). Превышение вызывает отказ `413 FILE_TOO_LARGE`.

### 3.4. Неизменяемый темпоральный журнал аудита (Event Sourcing Audit Trail)
В соответствии со ст. 19 п. 2 152-ФЗ и мерами ФСТЭК **РСБ.1**, **РСБ.3**, **РСБ.5**, система обеспечивает постоянную регистрацию и учет действий пользователей.

Особенности реализации:
- Таблица `interaction_events` имеет составное уникальное ограничение `UniqueConstraint("interaction_id", "sequence", name="uq_event_sequence")`.
- Поле `sequence` строго монотонно возрастает (`last_sequence + 1`), исключая пропуски или скрытые вставки.
- Каждое событие содержит моментальный снимок (`snapshot`) карточки со всеми связанными полями на момент совершения действия. В отчетах и аудите исторические данные не подменяются последующими изменениями справочников.
- Операции `UPDATE` и `DELETE` для строк `interaction_events` запрещены на уровне прикладной логики.

Кодовая реализация:
```python
# backend/app/models.py:139-154
class InteractionEvent(Base):
    __tablename__ = "interaction_events"
    __table_args__ = (
        UniqueConstraint("interaction_id", "sequence", name="uq_event_sequence"),
        Index("ix_event_temporal", "interaction_id", "effective_at", "received_at"),
    )
    id: Mapped[str] = mapped_column(String(64), primary_key=True, default=new_id)
    interaction_id: Mapped[str] = mapped_column(ForeignKey("interactions.id"), index=True)
    type: Mapped[str] = mapped_column(String(64))
    effective_at: Mapped[datetime] = mapped_column(DateTime(timezone=True))
    received_at: Mapped[datetime] = mapped_column(DateTime(timezone=True))
    sequence: Mapped[int] = mapped_column(Integer)
    actor_id: Mapped[str] = mapped_column(ForeignKey("users.id"))
    actor_name: Mapped[str] = mapped_column(String(200))
    payload: Mapped[dict] = mapped_column(JSON)

# backend/app/services.py:154-165
def append_event(db, item, actor, kind, at, **extra):
    payload = {"snapshot": interaction_dict(db, item), "visit_id": item.visit_id, **extra}
    last_sequence = db.scalar(select(func.max(InteractionEvent.sequence)).where(
        InteractionEvent.interaction_id == item.id)) or 0
    event = InteractionEvent(interaction_id=item.id, type=kind, effective_at=at, received_at=at,
                             sequence=last_sequence + 1, actor_id=actor.id, actor_name=actor.name, payload=payload)
    db.add(event)
    return event
```

## 4. Регламент обезличивания и архивации персональных данных

В соответствии со статьями 5, 21 Федерального закона № 152-ФЗ и Приказом Роскомнадзора № 996 от 05.09.2013, обработка персональных данных должна ограничиваться достижением конкретных, заранее определенных и законных целей. Персональные данные подлежат уничтожению либо обезличиванию по достижении целей обработки или в случае утраты необходимости в их достижении.

### 4.1. Основания для перевода в архив и обезличивания
1. **Завершение жизненного цикла партнерства:** Перевод взаимодействия в терминальный статус `completed` («Успешно завершено») или `cancelled` («Отменено»).
2. **Истечение срока хранения документов:** Истечение 3-летнего срока с даты подписания последнего договора или передачи учебных материалов.
3. **Отзыв согласия субъектом ПДн:** Поступление официального заявления от представителя образовательной организации об отзыве согласия на обработку персональных данных.

### 4.2. Метод обезличивания (Деперсонализация)
В качестве основного метода обезличивания в системе `rost_crm` применяется **метод введения идентификаторов (псевдонимизация)** в сочетании с **изменением состава (маскированием)** сведений в соответствии с п. 4 Приказа РКН № 996:

| Поле сущности | Исходный вид | Обезличенный вид после деперсонализации |
|---|---|---|
| `OrganizationContact.full_name` | Иванов Петр Сергеевич | Псевдоним: `Представитель [Хэш SHA-256]` (например: `Представитель 4f8b2a...`) |
| `OrganizationContact.phone` | +7 (999) 123-45-67 | Маскирование: `+7 (***) ***-**-**` |
| `OrganizationContact.email` | p.ivanov@university.ru | Маскирование: `p***v@***.ru` |
| `OrganizationContact.active` | `True` | `False` (деактивация контакта) |
| Файлы вложений (`Attachment`) | Физический файл на диске | Физический файл удаляется с диска (`file_path -> null`), в базе данных сохраняется только метаинформация и контрольная сумма $SHA\text{-}256$ для целей подтверждения неизменности исторического архива. |

### 4.3. Регламентные процедуры и порядок действий
1. **Инициация:** Запрос на деперсонализацию инициируется администратором системы (`admin`) через интерфейс управления или регламентным заданием по расписанию.
2. **Транзакционность:** Процедура обезличивания выполняется в единой транзакции БД с фиксацией в аудит-логе `InteractionEvent` с типом события `data_depersonalized`.
3. **Необратимость:** Таблица соответствия псевдонимов реальным ПДн в CRM не создается и не хранится. Восстановление исходных персональных данных из обезличенного состояния математически невозможно без внешнего изолированного контура доверенного оператора ПАО «Ростелеком».
4. **Сохранение аналитической ценности:** Обезличенные карточки сохраняют историческую привязку к вузам, программам, датам и статусам, что позволяет строить сквозные аналитические отчеты (`snapshot`, `activity`, `created`) без риска утечки персональных данных физических лиц.
