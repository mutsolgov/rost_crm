## 2. Архитектура бэкенда и модульный монолит (`backend/app/`)

Архитектура бэкенда организована по принципу модульного монолита с чётким разделением зон ответственности (SoC) и однонаправленным потоком управления.

```
backend/app/
├── main.py              # Тонкие контроллеры, Dependency Injection, глобальный error handler
├── schemas.py           # Строгие контракты данных Pydantic v2 DTO с валидацией
├── services.py          # Доменные сервисы, бизнес-правила, CAS-транзакции, выборка scope
├── models.py            # Декларативные модели SQLAlchemy 2.0, внешние ключи, индексы
├── workflow.py          # Детерминированный конечный автомат (FSM), реестр версий v1/v2
├── files.py             # Изолированная файловая подсистема, magic bytes (10 форматов ТЗ)
├── reports_export.py    # Экспорт аналитики в бинарный XLSX и векторный PDF на stdlib
├── importer.py          # Двухфазный мастер импорта каталогов (preview / commit)
├── integrations/        # Контур интеграций (нормализованный конверт 7.2, LMS Zion, Laravel)
└── db.py                # Пул соединений, настройки транзакций, SQLite busy_timeout=20s
```

### Ключевые архитектурные достоинства:
1. **Тонкие контроллеры (`main.py`)**: Роутеры не содержат SQL-запросов и не мутируют бизнес-сущности напрямую. Все параметры извлекаются через Pydantic DTO и `Depends()`, после чего управление передаётся доменным сервисам.
2. **Централизованная обработка ошибок (`errors.py`)**: Унифицированный формат ответа для всех клиентских и серверных ошибок в строгом соответствии с контрактом:
   ```json
   {
     "error": {
       "code": "REVISION_CONFLICT",
       "message": "Карточка изменена. Обновите данные.",
       "request_id": "634b3cbd-4e43-4282-93ca-28c88c6d3ac7",
       "details": null
     }
   }
   ```
3. **Строгие DTO Pydantic v2 (`schemas.py`)**: Исключают уязвимости Mass Assignment. Несанкционированные поля отсекаются на уровне парсинга тела запроса.
4. **Инкапсуляция транзакционных границ (`services.py`)**: Все мутации (создание, переходы, назначения, редактирование) выполняются в рамках единой транзакции БД с фиксацией в аудит-логе и таблице `CommandResult`.

## 3. Аудит чистоты кода и соблюдения принципов Ponytail

В соответствии с философией Ponytail (The Ladder: *«Лучший код — это код, который не пришлось писать»*) кодовая база бэкенда была подвергнута ревизии на предмет оверинжиниринга и избыточных зависимостей.

### 3.1. Анализ дерева зависимостей (`requirements.txt`)
В продакшн-окружении задействовано всего **6 фундаментальных библиотек**:
- `fastapi` & `uvicorn` — легковесный асинхронный HTTP-транспорт;
- `SQLAlchemy` & `psycopg` — стандарт объектно-реляционного отображения и драйвер PostgreSQL;
- `PyJWT` — стандартная проверка токенов RFC 7519;
- `pydantic` — декларативная валидация схем данных.

### 3.2. Отказ от тяжелых сторонних фреймворков в пользу Python stdlib
- **Генерация XLSX (MS Excel)**: Реализована в `backend/app/reports_export.py` с использованием стандартных модулей `zipfile` и `xml.sax.saxutils`. Исключены зависимости `openpyxl`, `pandas`, `xlsxwriter` (экономия более 150 МБ дистрибутива и исключение сотен транзитивных CVE).
- **Векторный PDF**: Реализован через потоковую генерацию структурированного PDF-потока. Исключены тяжелые и лицензионно-опасные библиотеки `reportlab`, `weasyprint`, `wkhtmltopdf`.
- **Файловая валидация**: Определение 10 допустимых форматов ТЗ по magic bytes (`\x89PNG`, `%PDF-`, `PK\x03\x04` и др.) реализовано стандартным побайтовым анализом без громоздкой библиотеки `python-magic`, требующей системных C-библиотек `libmagic`.
- **Аудит и хеширование**: Использованы нативные `hashlib.sha256` и `uuid.uuid4`.

### 3.3. Отсутствие мертвого кода и спекулятивных абстракций
- В кодовой базе отсутствуют пустые интерфейсы «на будущее» (No speculative interfaces).
- Отсутствуют избыточные шины событий и брокеры очередей — синхронизация и аудит работают в рамках транзакционной сессии БД, что гарантирует ACID-согласованность.

## 4. Конкурентность, CAS и гарантии защиты от дедлоков

Для исключения дедлоков и потерь обновлений (Lost Updates / Race Conditions) в проекте реализован механизм оптимистичной блокировки Compare-And-Swap (CAS) на базе поля `Interaction.revision`.

### 4.1. Механизм работы CAS
Все мутирующие операции (`PATCH /api/v1/interactions/{id}`, `/transitions`, `/assignments`, `/comments`, `/workflow/migrate/commit`) требуют передачи параметра `expected_revision`.
Запрос обновления выполняется атомарно на уровне SQL:
```python
result = db.execute(
    update(Interaction)
    .where(
        Interaction.id == item.id,
        Interaction.revision == expected_revision
    )
    .values(revision=expected_revision + 1, **values),
    execution_options={"synchronize_session": False}
)
if result.rowcount != 1:
    db.rollback()
    raise APIError("REVISION_CONFLICT", "Карточка изменена. Обновите данные.", 409)
```

### 4.2. Эмпирические результаты стресс-теста (20 параллельных потоков)
В рамках стресс-тестирования (`test_core_concurrency_and_security.py`) был запущен пул из 20 рабочих потоков (`ThreadPoolExecutor(max_workers=20)`), одновременно пытающихся изменить одну и ту же карточку с идентичным `expected_revision`.

**Результат выполнения:**
- **Успешных запросов (HTTP 200):** ровно **1**.
- **Отклоненных запросов с кодом конфликта (HTTP 409 REVISION_CONFLICT):** ровно **19**.
- **Итоговая ревизия карточки:** увеличилась ровно на **+1** (с 1 до 2).
- **События в аудит-логе:** зафиксировано ровно **1** событие `attributes_corrected`.
- **Дубликаты, дедлоки, повреждения состояния:** **0**.

### 4.3. Гарантии идемпотентности (`Idempotency-Key`)
Каждая мутирующая операция снабжается заголовком `Idempotency-Key` (до 200 символов).
- Таблица `CommandResult` транзакционно резервирует ключ до исполнения логики.
- Повторные запросы с тем же ключом и телом возвращают сохранённый ответ **без повторного применения мутаций** (0 дополнительных событий в логе, 0 повторных инкрементов ревизии).
- Попытка использовать тот же ключ с измененным телом запроса немедленно пресекается со статусом **HTTP 409 IDEMPOTENCY_CONFLICT**.
- Пустой заголовок, заголовок из пробелов или ключ длиннее 200 символов отклоняются валидатором со статусом **HTTP 422 VALIDATION_ERROR**.

## 5. Инварианты информационной безопасности (152-ФЗ, Приказ ФСТЭК №117)

### 5.1. Изоляция области видимости (Scope Isolation) и сокрытие сущностей (Strict 404)
В соответствии с нормами 152-ФЗ и требованиями ФСТЭК №117 система полностью исключает возможность горизонтальной эскалации привилегий (BOLA / IDOR):
- **Менеджер** видит только свои взаимодействия (`Interaction.owner_id == user.id`) и явно назначенные организации (`OrganizationAccess.can_create == True`).
- **Руководитель** видит только свою команду (`User.team_id == user.team_id`).
- **Администратор** не имеет неявного сквозного доступа к чужим бизнес-данным.

**Инвариант сокрытия (Strict 404 Not Found):**
Попытка менеджера А обратиться к карточке, вложению или комментарию менеджера Б по прямому ID возвращает **строго HTTP 404 Not Found**, а не HTTP 403 Forbidden. Это предотвращает сканирование пространства идентификаторов и скрывает сам факт существования чужих объектов.
Протестировано и верифицировано для:
1. `GET /api/v1/interactions/{id}` -> **404 NOT_FOUND**
2. `GET /api/v1/interactions/{id}/attachments/{att_id}/download` -> **404 NOT_FOUND**
3. `POST /api/v1/interactions/{id}/comments` -> **404 NOT_FOUND**
4. `PATCH /api/v1/interactions/{id}` -> **404 NOT_FOUND**
5. `POST /api/v1/interactions/{id}/transitions` -> **404 NOT_FOUND**
6. Доступ после смены ответственного руководителем -> **немедленный 404 NOT_FOUND** для прежнего менеджера.

### 5.2. Безопасность вложений и защита файлового хранилища
- **Белый список 10 форматов ТЗ**: Разрешены только `png, jpeg, pdf, zip, gzip, rar, doc, docx, xls, xlsx`. Исполняемые и скриптовые форматы (`.exe, .sh, .bat, .php, .js`) отклоняются с кодом **HTTP 422**.
- **Проверка сигнатур (Magic Bytes)**: Файлы проверяются по реальному содержимому, а не только по расширению.
- **Лимит 25 МБ**: Файлы свыше 25 МБ (26 214 400 байт) отклоняются с кодом **HTTP 413**.
- **Защита от Path Traversal**: Имена файлов санитизируются, пути на диске изолируются UUID-идентификаторами (`storage/attachments/{interaction_id}/{uuid}`), доступ организуется исключительно через защищенный контроллер с авторизацией.
- **Контрольные суммы**: Для каждого файла рассчитывается и валидируется $SHA\text{-}256$.

### 5.3. Защита от инъекций в формулы электронных таблиц (Formula Injection Defense)
При экспорте отчётов в формате XLSX любые текстовые поля, начинающиеся с символов `=`, `+`, `-`, `@`, автоматически экранируются префиксом `'` (одинарная кавычка) и сохраняются как `inlineStr`. Это гарантирует, что табличные процессоры (Excel, LibreOffice Calc) воспринимают данные строго как текст и блокируют выполнение внешних команд или макросов (`=CMD|' /C calc'!A0`, `@SUM`, `+HYPERLINK`).

### 5.4. Неизменяемый темпоральный аудит (`InteractionEvent`)
Любое изменение карточки (создание, смена статуса, корректировка атрибутов через PATCH, переназначение, добавление комментариев, прикрепление файлов, миграция workflow) фиксирует запись в таблице `InteractionEvent` с меткой времени UTC, идентификатором пользователя, сквозным номером `sequence` и детальным снимком изменений (`payload`).
