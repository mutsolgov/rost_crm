# Архитектурный фундамент для двух разработчиков

Подготовлено 19.09.2026 по исходному ТЗ и коду рабочего среза. Пакет описывает **целевую систему и оставшуюся работу**. Он не добавляет бизнес-функции в приложение и не подтверждает внедрение, нагрузку или нормативное соответствие.

Основное решение: сохранить **FastAPI + React + PostgreSQL + Keycloak**, разделить backend на модули, вынести тяжёлую работу в **Celery workers**, хранить jobs/outbox/inbox в PostgreSQL, использовать **Redis только как транспорт** и закрытое **S3-совместимое хранилище** для файлов. Workflow версионируется; отчёты строятся на сохранённом наборе строк; внешние системы подключаются через два независимых адаптера.

## Ключевые результаты анализа

Существующий код полезен: основные команды взаимодействий, проверка доступа, revision/idempotency, OIDC и небольшой исторический snapshot. Полного CRUD каталогов ещё нет. Отсутствуют contacts/contracts/licenses/deliveries, таблицы версий workflow и посещений, jobs/files/imports/adapters, требуемые отчётные форматы и учебные факты.

Из цели ТЗ отдельно выделено **R30**: заявки, число обучающихся и параллельных потоков. Количество карточек CRM не заменяет эти показатели. Формула общего рейтинга не задана — до её согласования система показывает проверяемые метрики отдельно.

Обязательства исходного документа сохранены: все десять типов вложений; импорт XLS/XLSX; отчёты XLS/XLSX/PDF и JSON; диаграммы PNG/PDF; оба реальных API; редактирование workflow; 50 пользователей и 10 действительно одновременно выполняемых отчётов; отклик ≤1 с. Требования к Archi, встроенной помощи, DOC/PDF и конкурсной презентации учтены в плане.

## Распределение работы

- **A:** platform/миграции, identity/access, каталоги/документы, взаимодействия/workflow, files backend, LMS/Laravel, запись learning facts, deployment.
- **B:** imports, reports/renderers, analytics, весь React, CI/e2e, встроенная помощь и конкурсный комплект.

Разделение позволяет обоим писать backend, сохраняя одного владельца каждого модуля. B начинает UI и импорт/отчёты на согласованных DTO/fakes, не ждёт завершения всего API A. Общие contracts и migration graph имеют ответственного интегратора и короткий handoff. Детальная нагрузка и возможная передача самостоятельных пакетов описаны в 04.

Остаток по текущей декомпозиции: **106–177 человеко-дней**. Это экспертный диапазон разработки/обычного review/проверок, не обещание срока и не стоимость формальных процедур заказчика. При суммарной доступности 1,5 человеко-дня в день — ориентир **14–24 рабочие недели** плюс внешние ожидания; после первых пакетов оценка пересчитывается. Хакатонный показ, полное покрытие и внедрение имеют разные gates.

Первый общий результат: C01–C07 + примеры ошибок/успеха. Затем A берёт **TD01/TD03** — контракты, модульные границы и Alembic; B — **TD02/TD04** — React features, consumer fixtures и CI. План первых пяти дней находится в 04; это старт реализации, а не новое исследование.

## Статус решений и прежних документов

Этот пакет уточняет `docs/planning` и задаёт текущую целевую архитектуру. Старый `implementation-contract.md` описывает только уже написанный срез. Старые R/AC и JSON-эталоны сохраняют смысл как исходная база; новые TD не смешиваются с прежними B-задачами. При расхождении проектных решений следовать этому пакету, а не считать оба варианта одновременно действующими.

Внешние неизвестные перечислены в 06: API и файлы заказчика, семантика лицензии/учебных метрик, права, объёмы нагрузки, размещение/ИБ и retention. Для начала разработки есть явные рабочие правила. Реальную интеграцию, нагрузку и эксплуатационный допуск можно принять только после соответствующих проверок.
