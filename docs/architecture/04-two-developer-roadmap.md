Дата: 19 сентября 2026 года. Статус: проект реализации; перечисленные задачи ещё не выполнены. Оценки относятся к оставшейся работе после существующего первого среза.

ИТ Школа Ростелекома.pdf», его первичный текст `work/source_text.txt` во внешнем рабочем каталоге, [спецификация первой версии](../planning/01-technical-specification.md), [старый backlog](../planning/02-development-plan.md), [приёмочные сценарии](../planning/03-acceptance-scenarios.md), [описание текущего среза](../../README.md), исходники `backend/app/`, `frontend/src/`, `compose.yaml`. ### 1.2. Пробел в прежней матрице и границы понятия «архив»

R01–R29 охватывают явные пункты списков функциональных и нефункциональных требований, но не выделяют самостоятельный проверяемый результат из цели на стр. 2: востребованность программ по заявкам на обучение, числу обучающихся и числу параллельных потоков. Предлагается добавить **R30 — учебные показатели и проверяемое сравнение востребованности программ**. Это детализация заявленной цели, а не новая придуманная формула рейтинга. Для R30 нужны определения метрик и доступность полей в API. До утверждения методики показатели показываются раздельно; неизвестные значения не превращаются в нули.

В старом плане учебная аналитика упомянута в B29, но не имеет отдельного R-ID и самостоятельного приёмочного сценария. Добавить **AC31**: один человек в двух программах, повторная заявка, отмена/завершение обучения, пересечение двух потоков и позднее событие; заранее заданы правильные показатели; повторный импорт не меняет итог; карточка CRM не засчитывается как заявка. Для агрегированных источников отдельно проверяется невозможность доказать уникальность людей между источниками.

Самостоятельное требование к разделу «Архив» в PDF отсутствует. Архивирование справочников и завершённых взаимодействий — проектное правило сохранения истории и удобства поиска, нужное для корректных отчётов. Оно не равно удалению данных и не определяет срок хранения. ZIP/GZIP/RAR — совершенно другой смысл слова: обязательные вложения.

Школы прямо названы в заголовке/цели, подробный путь описан для вузов. Модель сохраняет `organization.type`, а объём первого пилота школ подтверждает заказчик. Исключить школы без фиксации ограничения нельзя.

Уже подготовленные тесты первого среза и статические проверки — полезный материал. Их необходимо выполнить в воспроизводимой среде и сохранить результаты; наличие тестовых файлов не равно успешному прогону. Нагрузочная приёмка, реальная интеграция, контейнерный OIDC и эксплуатационная готовность не следуют из успешной сборки frontend.

## 3. Как двум людям работать одновременно

### 3.1. Постоянные зоны ответственности

Распределение по модулям, с одним владельцем каждого файла. Оба участника работают над бизнес-логикой backend; B одновременно владеет пользовательским интерфейсом. A не оставляет B ожидать готового сервера: контракт и примеры публикуются до реализации.

| Зона | Владелец | Целевые файлы/каталоги |
|---|---|---|
| Композиция backend, общие ошибки, UoW, команды, auth, инфраструктурный запуск | A | `backend/app/main.py`, `backend/app/platform/`, `backend/app/contracts/`, `backend/app/config.py`, `backend/app/db.py` |
| Identity/права, каталоги, взаимодействия, workflow | A | `backend/app/modules/identity/`, `catalogs/`, `interactions/`, `workflow/` |
| Файловый API/S3/карантин, интеграции, учебные факты | A | `backend/app/modules/files/`, `integrations/`, слой записи учебных фактов в `learning/` |
| Импорт, расчёт отчётов/рендеринг, аналитические проекции/метрики | B | `backend/app/modules/imports/`, `reports/`, `analytics/` |
| React и доступность | B | `frontend/src/app/`, `features/`, `contracts/`; перенос текущих `App.tsx`, `views/`, `api.ts`, `hooks.ts`, `styles.css` выполняет только B |
| Общая схема/миграционный граф, контейнеры, среда | A | `backend/alembic/`, `compose*.yaml`, `deploy/`, backend Dockerfile и зависимости инфраструктуры |
| Контрактные тесты/CI frontend, E2E, встроенная помощь | B | `frontend/tests/`, `tests/e2e/`, `frontend/src/features/help/`, `docs/user/`, `docs/admin/`, frontend Dockerfile |
| Контракты и эталоны | По доменному владельцу; общий индекс A | `contracts/openapi/`, `contracts/events/`, `contracts/fixtures/`; генерируемый клиент frontend обновляет B |
| Тесты модуля | Владелец модуля | `backend/tests/<module>/`; общую DB/auth fixture изменяет A, B добавляет локальные фикстуры |

Пути — целевая структура. Не требуется переносить весь репозиторий за один коммит. Обёртки/импорты совместимости сохраняют работу существующих маршрутов до переноса потребителей. Учебные факты `learning` и расчёты `analytics` имеют разные владельцы и не редактируют файлы друг друга.

Единоличное владение Alembic означает ответственность за итоговый граф, а не очередь на любое изменение таблицы. B приносит в PR модель своего модуля, спецификацию миграции, backfill и проверку данных; A резервирует следующий revision/parent и проверяет миграцию. Простые независимые миграции B может написать сам после резервирования ID. Только один человек одновременно меняет head; перед merge проверяется единственная голова и upgrade чистой/заполненной БД. Для review миграций закладывается ежедневное окно, а не ожидание конца спринта.

### 3.2. Контрактный handoff

Каждый handoff содержит пять частей: OpenAPI/JSON Schema; request/response/error examples; бизнес-инварианты; фиксированный проверочный набор; минимальный исполняемый fake. UI использует fake только в разработке; приёмка требует реального API.

| Контракт | Кто передаёт → кому | Содержание и срок передачи |
|---|---|---|
| C01. Actor/Scope и команды | A → B | actor_id, permissions, проверка текущей области; revision/CAS, Idempotency-Key, единый error envelope. Предварительная версия есть в архитектурном пакете, внутреннее закрепление — дни 1–2. |
| C02. Domain read/write ports | A → B | Получение доступных каталогов/карточек; команды импорта/интеграции; запрет прямого UPDATE таблиц interactions из чужих модулей. Дни 1–2, реализация в TD08/TD10. |
| C03. Jobs/outbox | A → B | job_id, type, requester, input_ref, schema_version; состояния queued/running/succeeded/failed/cancelled; retry/cancel/error/result; без пароля/токена/байтов файла в Redis. Дни 1–2, реализация TD06. |
| C04. Files | A → B | Загрузка/завершение, file_id, scan status, привязка к status visit, проверенное скачивание, срок хранения результата. Контракт до начала TD12/TD13/TD14; реализация TD12. |
| C05. Workflow/history | A → B | template/version/state/transition ID, декларативные guards, draft/validation/publish/migration preview; история посещений. До начала TD16/TD17; базовые примеры — первая неделя. |
| C06. Reports/metrics | B → A | Семантика периода/as_of/knowledge_cutoff, колонки/фильтры, report definition version, dataset/result refs; ожидания учебных фактов. Первая версия в TD01/TD02, детализация TD19. |
| C07. External records/learning facts | A → B | Источник/внешний ID/ревизия/происхождение, заявка/учебный поток/зачисление либо помеченный агрегат; исходные и канонические даты. До TD22/TD26, реальные поля после X02. |

Правило изменения: автор публикует schema diff и новые примеры; другой разработчик проверяет свой потребитель. Совместимое добавление опционального поля допустимо в малом PR. Переименование/изменение смысла требует версии/переходного адаптера; молча менять контракт в ходе реализации нельзя. Один доменный сервис владеет транзакцией; общие UoW и domain ports исключают независимые `commit()` из импортера, интеграции и outbox.

### 3.3. Ежедневный ритм

Рабочие ветки `feat/tdNN-...`, небольшие PR с одной проверяемой целью; никакой отдельной многонедельной ветки «backend» или «frontend». На каждый день у каждого человека одна основная задача; максимум одна дополнительная задача, ожидающая review. Ежедневно — короткий обмен изменениями контрактов и выделенное окно взаимного review. На общий стенд изменения попадают несколько раз в неделю. Merge требует совместимых схем и зелёных проверок; merge не равен выпуску в среду заказчика.

## 4. Пакеты работ и зависимости

Оценка — суммарные человеко-дни инженерной работы, включая локальные тесты, обычный review и обновление документации задачи. «Владелец» — ведущий исполнитель, а не запрет на взаимную помощь. Диапазоны экспертные, предполагают знание стека. Внешнее ожидание X01–X06 и неизвестные формальные процедуры не включены. Табличные зависимости означают готовность к итоговой приёмке пакета; UI/fake/schema можно делать раньше по контракту.

Общие зоны: **platform** = `backend/app/platform/` и `contracts/`; **M/name** = `backend/app/modules/name/`; **F/name** = `frontend/src/features/name/`; **contracts** = `contracts/`. В каждом пакете владелец дополняет tests своего модуля.

## 5. Оценка и порядок движения

| Группа | Задачи | A, чел.-дни | B, чел.-дни | Всего, чел.-дни |
|---|---|---:|---:|---:|
| F0 — фундамент | TD01–TD07 | 11–18 | 6–10 | 17–28 |
| F1 — операции | TD08–TD18 | 16–26 | 14–25 | 30–51 |
| F2 — отчётность/интеграции | TD19–TD28 | 11–19 | 17–27 | 28–46 |
| F3 — приёмка/передача | TD29–TD41 | 17–29 | 14–23 | 31–52 |
| **Итого** | **41 пакет** | **55–92** | **51–85** | **106–177** |

Суммы по владельцу — труд пакетов соответствующего ведущего исполнителя; взаимное review уже включено в пакеты и не прибавляется второй раз. Это не точный табель двух людей: нагрузка review распределяется между ними.

Прежние 121–209 человеко-дней оценивали полный проект до реализации текущего среза и до подтверждения команды из двух человек. Новый ориентир **106–177 человеко-дней оставшейся работы** учитывает повторное использование среза и документов, но не объявляет непроверенный код готовым. Вычитать один диапазон из другого как «точно уже отработанные дни» нельзя: изменилась декомпозиция и уточнились пробелы.

При суммарной фактической производительности двух участников 1,5 человеко-дня в рабочий день это примерно **71–118 рабочих дней, или 14–24 рабочих недели**, без внешнего ожидания. Это пример расчёта, не обещание срока. Чистое деление на двух даёт 53–89 дней, но игнорирует последовательные зависимости, review и ограничения доступности. После TD01–TD06 оценки пересчитываются по реальной скорости команды; общий резерв сверх диапазона не включён.

У A больше объёма. Если A становится узким местом, B может взять самостоятельный адаптер сайта TD24 или техническую часть Archi TD36 после закрытия своих текущих задач; handoff явно меняет владельца этих каталогов. Перенос не выполняется одновременно с правками A. Не стоит устранять дисбаланс общей работой в одном `services.py`.

Рекомендуемый порядок волн:

1. **Контракты и вертикальный каркас:** A — TD01/TD03/TD05/TD06; B — TD02/TD04/TD07. На выходе — общий стенд, миграции, API policy, jobs и контрактный frontend.
2. **Рабочее место и доказательство импорта:** A — TD08/TD10/TD12; B — TD09/TD11/TD13, затем TD14/TD15. Параллельно A начинает TD16/TD18, пока B завершает импорт и TD17.
3. **Две независимые ветви:** A — TD22/TD23/TD24/TD26; B — TD19/TD20/TD21. Учебный контракт TD26 передаётся B заранее, чтобы TD27 не ждал реального подключения.
4. **Приёмка и комплект:** A — TD30/TD34/TD36/TD38; B — TD25/TD28/TD29/TD31/TD35/TD37. TD32/TD33 соединяют результаты; пилот TD39–TD41 только после своих внешних условий.

Критический путь полного внедрения проходит через данные/права → jobs → файловый и интеграционный контур → отчёты/сверку → нагрузку/восстановление → допуск данных → пилот. Во время задержки реального LMS/B2B API продолжаются parser/fixtures/contract tests, редактор, файлы, отчёты и документация; условие «реально подключено» при этом не закрывается.

Ожидание API или решения заказчика — статус блокировки конкретной задачи, а не основание останавливать оба потока. После появления контракта его отличие от fake оценивается отдельно. ## 10. Общий Definition of Done

Пакет закрыт, когда код/миграции/контракты прошли review второго разработчика, осмысленные проверки бизнес-правил выполнены, документация обновлена, результат работает на общем стенде и есть ссылка на доказательство. Для HTTP-пути это включает OIDC/права, устойчивый error code и описание OpenAPI; для записи — транзакцию/CAS/идемпотентность/аудит; для фоновой задачи — повтор/сбой/права на результат; для UI — ошибки/мобильность/сохранность контекста. Это общая работа внутри оценки пакета, а не добавочный скрытый проект.

Задачи разработки не закрываются только скриншотом fake, наличием схемы БД, сформированным файлом без проверки содержимого или одной удачной ручной попыткой. Для контроля процесса достаточно карточки TD с владельцем, dependency, ссылкой на PR, результатом тестов и оставшимися условиями. Проценты «готовности CRM» без этих свидетельств не используются.
