# Приёмочные сценарии CRM ИТ Школы

Дата: 17 сентября 2026 года. Статус: проект приёмочного протокола для согласования.

Сценарии предназначены для проверки будущей реализации. **CRM по этим сценариям ещё не испытывалась.** Проверен только синтетический эталон отчётности: его ожидаемые результаты независимо пересчитаны скриптом.

R01–R29 — идентификаторы требований из подготовленного анализа PDF. AC01–AC30 — предлагаемые приёмочные сценарии. Ссылки на R показывают покрытие требования, но не превращают дополнительные критерии этого протокола в дословные требования ТЗ.

Все правила сверх ТЗ — проектные предложения для согласования: версия workflow и её миграция, семантика исторических отчётов, политика конфликтов и повторов, области доступа, проверка содержимого файлов, правила кэша, диагностика, восстановление и пилот. Любые размеры наборов, число повторов, лимиты файлов, оборудование, браузеры и дополнительные временные пределы испытаний также являются предложениями; ниже они не выдаются за установленные заказчиком параметры. Из ТЗ непосредственно взяты предел отклика в 1 секунду, 50 параллельных пользователей и минимум 10 параллельно строящихся отчётов.

## Условия и доказательства

До прогона зафиксировать версию приложения, конфигурацию среды, версию данных, учётные записи, матрицу доступа и одобренные решения по неоднозначностям. Синтетические данные отделить от реальных. Для каждого AC записывать «не запускался / пройден / не пройден / заблокирован», фактический результат, ссылку на доказательства и дефект при расхождении.

Имитатор API подходит для разработки и проверки сбоев. Приёмку реальной интеграции подтверждает отдельный прогон по действующему контракту источника. Скриншот сам по себе не доказывает сохранение данных, ограничение доступа или правильность отчёта.

Эталон: [05-report-fixture.json](./05-report-fixture.json). Все названия, организации и пользователи вымышлены. Набор содержит 6 взаимодействий, 23 канонических события, 3 примера доставки и 12 ожидаемых результатов; это размер тестового примера, а не ограничение системы.

## Сценарии

### AC01. Справочники и независимость взаимодействий

**Покрытие:** R01, R03, R05.

**Дано:** согласованные справочники и собственный ID каждого взаимодействия. Организация, nullable программа, nullable продукт и цикл описывают взаимодействие; кортеж не подменяет его ID.

**Действие:** загрузить каталоги; создать или импортировать I1, I2, I5 и I6 из эталона; изменить состояние I1; повторно открыть данные после перезапуска.

**Ожидается:** I1 и I2 одного вуза независимы; I6 другого цикла не объединяется с I1; I5 сохраняется без выдуманной программы и продукта. Связи и значения переживают перезапуск. Правила обязательности полей и разрешения повторов — предложение, согласуемое с заказчиком.

**Доказательства:** записи с ID до/после действия, ответы API и история изменений.

### AC02. Импорт настоящих XLS и XLSX

**Покрытие:** R02, R03.

**Дано:** согласованный маппинг; отдельные корректные файлы XLS и XLSX с полями ТЗ: название вуза, вендор, ПО, номер договора, подписание лицензии, срок действия, статус передачи, менеджер, ответственные вуза, комментарий.

**Действие:** проверить лист и маппинг, выполнить первоначальный импорт и обновление известных объектов в обоих форматах.

**Ожидается:** значения попадают в согласованные сущности, новые объекты создаются, известные обновляются по устойчивым ключам. Неопределённый смысл даты или срока не заменяется придуманным значением. Переименованный CSV/XLSX не принимается за корректный XLS.

**Доказательства:** исходные файлы, маппинг, протокол строк и сравнение значений в системе.

### AC03. Ошибки, пустые значения и повторы импорта

**Покрытие:** R02, R03, R20.

**Дано:** предлагаемые правила обработки ошибок, пустых ячеек и конфликтов; файл с корректной строкой, неизвестной ссылкой, дублем и некорректным значением.

**Действие:** выполнить предпросмотр и импорт; затем повторно отправить тот же файл; отдельно проверить попытку очистить заполненное поле пустой ячейкой.

**Ожидается:** ошибки привязаны к строке и полю; частичное применение либо полный отказ точно соответствуют принятой политике. Повтор не создаёт случайных дублей. Пустая ячейка не удаляет данные без предусмотренного правила; итог обработки виден пользователю.

**Доказательства:** счётчики созданных/обновлённых/пропущенных записей, отчёт об ошибках и проверка сохранённых данных.

### AC04. Keycloak и жизненный цикл сессии

**Покрытие:** R14, R15.

**Дано:** подключённый Keycloak и тестовые учётные записи назначенных ролей.

**Действие:** войти и выйти; обратиться к защищённому API без авторизации, с истёкшим или недействительным токеном; выполнить повторную авторизацию.

**Ожидается:** защищённые данные доступны только с допустимой сессией и предметными правами. После окончания сессии интерфейс предлагает вход и не выдаёт закрытый ответ из старого состояния. Предлагаемая политика завершения сессии и очистки локальных данных зафиксирована отдельно.

**Доказательства:** ответы API и журнал авторизации без паролей и токенов в отчёте.

### AC05. Текущий доступ во всех каналах

**Покрытие:** R15, R27.

**Дано:** scope_now эталона; U_MANAGER_A видит I2/I5, U_MANAGER_B — I1/I3/I6, U_LEAD — всё перечисленное, кроме I4. U_TECH_ADMIN без предметных прав имеет пустую область — это предлагаемая политика.

**Действие:** запросить чужую I4 через карточку, прямой API, поиск, счётчик, диаграмму, экспорт, вложение и фоновое задание; выполнить FX-S07.

**Ожидается:** ни один канал не раскрывает чужие строки, содержимое файлов или агрегаты. FX-S07 возвращает пустой результат. Техническая роль не расширяет область автоматически при выбранной политике.

**Доказательства:** матрица проверок по каналам и ответы сервера; скрытие кнопки без серверной проверки недостаточно.

### AC06. Назначение менеджера и отзыв доступа

**Покрытие:** R15.

**Дано:** руководитель с правом назначения и пользователь без такого права; для доступной карточки заранее сформирован отчёт.

**Действие:** руководителем назначить, заменить и снять ответственного организации; отдельно переназначить выбранную карточку новому менеджеру; повторить действие обычным пользователем; после отзыва доступа запросить карточку и уже сформированный файл. Снятие ответственного организации не обнуляет автоматически владельцев существующих карточек, которым по проектной модели требуется owner_id.

**Ожидается:** руководитель действует только в согласованной области; запрещённое назначение отклонено. История сохраняет прежнего ответственного. Утрата права применяется к следующим обращениям и скачиванию. Предложение: файл, содержащий уже недоступные строки, целиком не выдаётся; пользователь может сформировать новый отчёт по оставшимся правам.

**Доказательства:** события назначений, область доступа до/после, результат повторного скачивания.

### AC07. Базовый процесс и все пункты бизнес-пути

**Покрытие:** R05, R06.

**Дано:** согласованный базовый шаблон из 04-base-workflow.json и сопоставление со всеми 14 пунктами ТЗ.

**Действие:** пройти основной путь, вариант без корректировки документов и допустимый возврат; открыть наглядное состояние и историю взаимодействия.

**Ожидается:** обязательные пункты не потеряны, необязательная корректировка может быть пропущена по правилам. Сквозной контроль каждого этапа объяснён и проверяем; он не обязан быть четырнадцатой колонкой. Запрещённый переход отклоняется. Конкретный граф переходов является проектным предложением.

**Доказательства:** матрица покрытия 14 пунктов, история переходов и проверка запрета.

### AC08. Редактор, версии и перенос действующего workflow

**Покрытие:** R06.

**Дано:** предлагаемые правила неизменности опубликованной версии и явного переноса; карточка использует опубликованный шаблон.

**Действие:** создать новый шаблон; переименовать этап и изменить переходы в новой версии; опубликовать её; затем перенести действующую карточку с сопоставлением этапов.

**Ожидается:** новая карточка использует выбранную новую версию, старая сохраняет прежнюю до явного переноса. Удалённый этап не оставляет карточку без состояния. Перенос проверяет совместимость и оставляет след в истории; исторический отчёт воспроизводится по принятой политике.

**Доказательства:** обе версии, карточки до/после, предпросмотр переноса и журнал операции.

### AC09. Переход, комментарий и одновременное редактирование

**Покрытие:** R05, R07, R16, R20.

**Дано:** одна карточка открыта у двух пользователей; предлагается контроль версии записи.

**Действие:** выполнить переход с комментарием; вторым пользователем отправить изменение устаревшей версии; вернуть карточку на прежний этап допустимым переходом.

**Ожидается:** успешное изменение и комментарий сохранены вместе и связаны с автором/событием. Устаревшая запись не затирает новое состояние; конфликт объяснён. Повторные посещения этапа различимы. Страница не перезагружается, позиция и фильтры не сбрасываются. Комментарий обязателен лишь при явно согласованном условии.

**Доказательства:** журнал событий, версии записей и запись пользовательского сценария.

### AC10. Все типы вложений и проверка прав

**Покрытие:** R08, R15, R27.

**Дано:** безопасные синтетические файлы PNG, JPEG, PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS, XLSX; согласованы лимиты и правила проверки.

**Действие:** загрузить и скачать каждый тип; проверить связь с конкретным этапом/посещением; обратиться без права; проверить неверное расширение и превышение согласованного лимита.

**Ожидается:** поддерживаемые корректные файлы сохраняются без повреждения и выдаются только уполномоченному пользователю. Нарушение принятой политики даёт понятную ошибку. Проверка содержимого и карантин — предлагаемые эксплуатационные меры. Прикрепление архива не требует его автоматической распаковки.

**Доказательства:** список типов, контрольные суммы до/после и отрицательные проверки доступа.

### AC11. Исторический snapshot до и после позднего события

**Покрытие:** R04, R09, R11.

**Дано:** семантика snapshot как проектное предложение: при as_of_inclusive=true (по умолчанию и в эталонном JSON) effective_at ≤ as_of и received_at ≤ knowledge_cutoff; состояние восстанавливается по известным событиям. Для календарного «конца дня» отдельно проверить as_of=начало следующего дня и as_of_inclusive=false: событие ровно на этой границе не включается.

**Действие:** выполнить FX-S01 и FX-S02 с одинаковым as_of 2026-09-05T23:59:59Z, но разным knowledge_cutoff.

**Ожидается:** в обоих случаях доступны I1/I2/I3/I5/I6. В FX-S01 у I2 document_signing; в FX-S02 — materials_transfer из-за I2-T2, полученного 7 сентября. Итого по этапам: соответственно exchange/signing/materials/classes = 1/1/2/1 и 1/0/3/1. Прочие строки неизменны; отчёт показывает обе временные отсечки.

**Доказательства:** полное сравнение с expected_results двух кейсов, включая строки и группировки.

### AC12. Исторический ответственный отдельно от текущего права

**Покрытие:** R04, R09, R15.

**Дано:** I1 был назначен M1 до 6 сентября, затем M2; scope_now применяется независимо от as_of.

**Действие:** выполнить FX-S03–FX-S06.

**Ожидается:** в FX-S03 I1 находится в classes у M2, включая переход ровно на as_of. На дату 5 сентября фильтр исторического M1 даёт руководителю I1/I2/I5 (FX-S04), U_MANAGER_A — только I2/I5 (FX-S05), U_MANAGER_B — I1 с историческим M1 (FX-S06). Историческое владение не возвращает отозванное право.

**Доказательства:** строки с historical_owner_id, отдельно текущая область доступа и журнал назначения.

### AC13. Activity: границы периода и уникальные переходы

**Покрытие:** R04, R09, R13.

**Дано:** предлагаемая семантика activity: интервал [from,to), только уникальные transition event_id; создание и назначения не считаются переходами.

**Действие:** выполнить FX-A01 для [2026-09-01T00:00:00Z, 2026-09-10T00:00:00Z) с knowledge_cutoff 2026-09-15T12:00:00Z.

**Ожидается:** ровно 6 переходов по 3 взаимодействиям: I1-T2, I2-T1/T2/T3, I3-T1/T2. I1-T2 на нижней границе включён; I1-T1 до начала и I1-T3 ровно на верхней границе исключены. Повторная доставка I2-T1 не добавляет переход. События I4 не доступны руководителю.

**Доказательства:** сверка списка event_id, totals и всех группировок FX-A01.

### AC14. Activity: знание, смена владельца и область доступа

**Покрытие:** R04, R09, R15.

**Дано:** historical_owner в activity определяется на effective_at каждого перехода по назначениям, известным к knowledge_cutoff; это предложение для согласования.

**Действие:** выполнить FX-A02–FX-A05.

**Ожидается:** FX-A02 с ранним knowledge_cutoff содержит 3 известных перехода. FX-A03 с владельцем M1 — 4 перехода. FX-A04 за период до 11 сентября с M2 — I1-T3, I3-T1, I3-T2, всего 3. FX-A05 для U_MANAGER_A включает только 3 перехода I2: I1 не возвращается в результат из-за прежнего владельца.

**Доказательства:** полное сравнение с expected_results и объяснение отличий от FX-A01.

### AC15. Все фильтры и выбор колонок

**Покрытие:** R04, R09.

**Дано:** эталон и дата/knowledge_cutoff FX-S03; согласованная трактовка направления и программы.

**Действие:** совместить фильтры O1, P1/D1, S1, classes и исторический M2; менять набор колонок, включая вуз, направление, продукт, статус, ответственного; проверить пустой результат и карточку без программы/продукта.

**Ожидается:** совместная выборка содержит I1/I6; независимые фильтры не перезаписывают друг друга. Колонки соответствуют выбору пользователя. I5 не теряется из нефильтрованного списка и не получает выдуманные названия. Представление «Не задано» как специального фильтра — предложение.

**Доказательства:** параметры запроса, ID строк, выбранные колонки и отрицательная комбинация фильтров.

### AC16. Отчёты XLS, XLSX и PDF

**Покрытие:** R09, R10.

**Дано:** согласованный отчёт с фильтрами, выбранными колонками, кириллицей и пустыми значениями.

**Действие:** получить XLS, XLSX и PDF для одного набора данных; открыть подходящими средствами; сравнить с экраном и эталоном.

**Ожидается:** каждый файл действительно имеет заявленный формат; строки, числа и ограничения доступа совпадают. PDF читаем, таблица не обрезана, заголовки/фильтры однозначны. Для ограничения строк конкретного формата предлагается явная обработка переполнения, а не тихое усечение.

**Доказательства:** три файла, результат определения формата, сверка строк/итогов и просмотр всех страниц PDF.

### AC17. Достоверные диаграммы и PNG/PDF

**Покрытие:** R11, R28.

**Дано:** данные FX-S02 и FX-A01; согласованные диаграммы состояния и переходов.

**Действие:** построить диаграммы и выгрузить каждую в PNG/PDF; изменить фильтр; проверить нули и отсутствие данных.

**Ожидается:** числа совпадают с соответствующим табличным расчётом и expected_results. Указаны показатель, единица, период/as_of и актуальность. Количество взаимодействий не подписано как число студентов; «нет данных» не превращается в ноль без правила. Шкалы, подписи и цвета позволяют прочитать значения без искажения.

**Доказательства:** исходные агрегаты, изображения, PDF и сверка с таблицей.

### AC18. Реальные интеграции LMS и сайта

**Покрытие:** R12, R13, R23.

**Дано:** действующие согласованные контракты обоих источников, доступы и владельцы полей; приложение не хранит секреты в исходниках.

**Действие:** получить JSON каждого источника, сопоставить известную запись и создать новую; проверить попадание данных в существующий/новый workflow.

**Ожидается:** оба источника подключены фактически, внешние ID сохранены, поля обновлены согласно владению и области изменений. Неоднозначное сопоставление не объединяет карточки молча. Если доступов нет, статус AC — «заблокирован», а результат имитатора указывается отдельно.

**Доказательства:** обезличенные запросы/ответы, версии контрактов, журнал обработки и сопоставленные ID.

### AC19. Дубли API, сбой и конфликт содержимого

**Покрытие:** R12, R13, R20.

**Дано:** предлагаемый ключ события event_id и правило первого received_at; при отсутствии event_id у источника согласуется отдельный ключ идемпотентности.

**Действие:** дважды доставить I2-T1 по event_deliveries; прервать обработку пакета и повторить; отправить тот же ID с изменённым содержимым.

**Доказательства:** канонический журнал, протокол доставок/повтора, курсор либо контрольная позиция обработки.
