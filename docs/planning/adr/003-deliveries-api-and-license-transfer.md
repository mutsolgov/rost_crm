# ADR 003: Интеграция подсистемы выдачи ПО (Deliveries API) и реестра лицензий

**Статус:** Принято к исполнению  
**Дата:** 28 сентября 2026 года  
**Автор:** Ведущий инженер проекта rost_crm  
**Связанные задачи:** SWE-26, D-04-1, D-04-2, D-04-3  
**Связанные сценарии приёмки:** AC01, AC06, AC07, AC12, AC26  

---

## 1. Контекст и проблема

В ходе аудита этапа 4 (Contracts, Licenses & Deliveries) были выявлены три архитектурных разрыва:
1. **D-04-1 (Отсутствие REST API для поставок ПО):** Модели данных `Delivery` и `DeliveryItem` были объявлены в `backend/app/models.py`, но не имели публичных маршрутов API. Клиенты не могли программно зафиксировать факт передачи программного обеспечения и лицензионных пакетов организации.
2. **D-04-2 (Отсутствие интерфейса поставок в карточке взаимодействия):** В пользовательском интерфейсе карточки (`frontend/src/views/InteractionPage.tsx`) отсутствовал блок управления поставками и модальное окно регистрации выдачи ПО.
3. **D-04-3 (Отсутствие реестра лицензий в справочниках):** В разделе «Справочники» (`frontend/src/views/CatalogPage.tsx`) отображалась панель договоров, но отсутствовала панель учета лицензий с их статусами передачи (`transfer_status`) и сроками действия.

---

## 2. Архитектурное решение

### 2.1. Backend REST API (`backend/app/services.py`, `backend/app/main.py`)
- Реализованы сервисные функции:
  * `get_interaction_deliveries(db, user, interaction_id)`: выборка поставок с дочерними позициями, защищенная строгой проверкой области видимости `scoped_interaction` (152-ФЗ / Zero-Oracle: чужие или несуществующие карточки возвращают `404 Not Found`).
  * `create_delivery(db, user, interaction_id, body, key)`: атомарное создание записей `Delivery` и `DeliveryItem`, поддержка идемпотентности через `Idempotency-Key` (таблица `command_results`), CAS-проверка ревизии карточки, фиксация неизменяемого события `delivery_recorded` в `InteractionEvent`.
- Смонтированы эндпоинты в `main.py`:
  * `GET /api/v1/interactions/{interaction_id}/deliveries` (tags=["deliveries"])
  * `POST /api/v1/interactions/{interaction_id}/deliveries` (status_code=201, tags=["deliveries"])

### 2.2. Frontend UI (`frontend/src/views/InteractionPage.tsx`, `api.ts`, `types.ts`)
- Добавлены типы `DeliveryRecord`, `DeliveryItemRecord`, `CreateDeliveryPayload` в `types.ts`.
- В клиент `ApiClient` добавлены методы `getDeliveries` и `createDelivery`.
- В `InteractionPage.tsx` встроена секция «Выдача ПО и лицензий (Поставки)»:
  * При отсутствии поставок отображается лаконичное пустое состояние.
  * При наличии записей — карточки поставок с бейджами версий, канала передачи, получателя и статуса «Подтверждено».
  * Интерактивное модальное окно `RegisterDeliveryModal` с валидацией полей, привязкой к контактам и лицензиям организации.
  * Реактивное обновление интерфейса (SPA) без перезагрузки страницы браузера.
  * Автоматическое отражение события `delivery_recorded` в таймлайне решений карточки.

### 2.3. Панель «Лицензии ПО» в каталогах (`frontend/src/views/CatalogPage.tsx`)
- В раздел «Справочники» добавлена панель «Лицензии ПО», выводящая список лицензий из `catalogs.licenses` с наименованием продукта, сроком действия и бейджами статуса передачи (`Передана`, `Ожидает`, `Отозвана`).

---

## 3. Последствия и соответствие инвариантам
1. **152-ФЗ / Приказ ФСТЭК №117:** Полная изоляция карточек и поставок на уровне строк БД; доступ к чужому ID возвращает 404 Not Found.
2. **Принцип разумной достаточности:** 0 новых внешних npm и pip библиотек. Использованы стандартные компоненты и стили дизайн-системы Ростелеком Gen2.
3. **Целостность спецификаций:** Директория `docs/architecture/` сохранена строго неизменной (0 байт diff).
