### 2.3. Механика запуска сервера и режимы транспорта (Live vs In-Process)
Бенчмарк должен поддерживать **два режима работы**:
1. **In-Process ASGI Режим (`--in-process` или по умолчанию без `--url`):**
   - Использует `httpx.ASGITransport(app=app)`.
   - Запускается напрямую внутри одного процесса Python без открытия сетевых сокетов и без фонового процесса uvicorn.
   - Идеально подходит для CI/CD, песочниц, офлайн-проверок и автоматизированных тестов `pytest`.
2. **Сетевой HTTP Режим (`--url http://host:port`):**
   - Использует стандартный `httpx.AsyncClient(base_url=url, limits=Limits(max_connections=100, max_keepalive_connections=50))`.
   - Проверяет реальный сетевой стек Uvicorn/FastAPI/Reverse Proxy на выделенном стенде или в Docker Compose.

## 3. Критические эмпирические находки и узкие места (Bottlenecks)

В ходе предварительного нагрузочного профилирования на 50 пользователей + 10 отчётов выявлены **четыре критических архитектурных фактора**, определяющих соблюдение R18 (latency ≤ 1.0s):

### Узкое место №1: Дефолтный лимитер пула потоков AnyIO (Thread Starvation)
- **Симптом:** При одновременном запуске 50 пользователей и 10 аналитических потоков (всего 60 параллельных задач) средняя задержка подскакивала с 50 мс до 1400 мс, а P95 превышал 1.8 с.
- **Первопричина:** FastAPI выполняет синхронные обработчики роутов (`def get_interactions(...)`) через Starlette `run_in_threadpool`, который опирается на `anyio.to_thread.run_sync`. По умолчанию `anyio.to_thread.current_default_thread_limiter().total_tokens == 40`. При 60 одновременных запросах 20 задач зависали в очереди ожидания свободного потока AnyIO еще до обращения к базе данных!
- **Решение:** В точке входа бенчмарка и в конфигурации приложения необходимо явно устанавливать размер пула потоков:
  ```python
  import anyio
  anyio.to_thread.current_default_thread_limiter().total_tokens = 120
  ```

### Узкое место №2: Межпоточная блокировка SQLite при `StaticPool`
- **Симптом:** При использовании SQLite in-memory (`sqlite:///:memory:`) возникала фатальная ошибка `sqlalchemy.exc.InterfaceError: (sqlite3.InterfaceError) bad parameter or other API misuse`.
- **Первопричина:** `backend/app/db.py` для `:memory:` подключает `StaticPool`, удерживающий ровно одно соединение SQLite. Попытка параллельных потоков пула AnyIO одновременно вызывать `cursor.execute` на общем дескрипторе приводит к гонке и падению драйвера.
- **Решение:** Для in-process бенчмарка на SQLite необходимо использовать файловую базу (например, временный файл) с режимом WAL (`PRAGMA journal_mode=WAL;`, `PRAGMA synchronous=NORMAL;`), `timeout=30`, и пулом `NullPool` (или настроенным `QueuePool(size=60, max_overflow=20)`), где каждый рабочий поток получает собственный изолированный дескриптор.

### Узкое место №3: Лишние SQL-запросы в `services.py:validate_filters`
- **Симптом:** Эндпоинт `GET /api/v1/interactions` выполнял 2 скрытых SQL-запроса на получение всех доступных ID организаций (`visible_organization_ids`) даже тогда, когда клиент не передавал параметр `organization_id`.
- **Первопричина:** В строке 419 `backend/app/services.py`:
  ```python
  if not set(organization_ids) <= visible_organization_ids(db, user):
  ```
  Python сначала вычисляет правое выражение `visible_organization_ids(db, user)`, выполняя SQL-запрос `SELECT organization_id FROM interactions...`, даже если `organization_ids` пуст (`set() <= X` всегда `True`).
- **Решение:** Добавить короткое замыкание (short-circuit):
  ```python
  if organization_ids and not set(organization_ids) <= visible_organization_ids(db, user):
  ```
  Это экономит сотни SQL-запросов в секунду под параллельной нагрузкой.

### Узкое место №4: 152-ФЗ изоляция и корректное распределение карточек по ролям
- **Симптом:** При случайном выборе ID карточки для запроса `GET /api/v1/interactions/{id}` происходили ошибки 404 (Not Found).
- **Первопричина:** Согласно 152-ФЗ и правилам `AGENTS.md`, попытка менеджера открыть чужую карточку обязана возвращать `404 Not Found`. В сиде `ix-1..ix-3` принадлежат `manager-a`, а `ix-4..ix-6` — `manager-b`. Администратор же по умолчанию вообще не имеет видимых карточек в реестре (только системные разделы).
- **Решение:** Профиль симулированного пользователя должен соблюдать ролевую матрицу:
  - 20 виртуальных пользователей `manager-a` обращаются к `ix-1, ix-2, ix-3`.
  - 20 виртуальных пользователей `manager-b` обращаются к `ix-4, ix-5, ix-6`.
  - 8 виртуальных пользователей `supervisor` обращаются ко всем карточкам команды (`ix-1..ix-6`), а также к дашборду и метрикам.
  - 2 виртуальных пользователя `administrator` обращаются к системным разделам (статус шлюза интеграций, очередь сверки, справочники, конфиг).

### 4.4. Сбор и агрегация метрик

Для каждого запроса фиксируется запись:
```python
@dataclass
class RequestRecord:
    endpoint: str        # e.g. "GET /api/v1/interactions"
    category: str        # "interactive" | "analytical" | "administrative"
    latency_ms: float    # Задержка в миллисекундах
    status_code: int     # HTTP статус ответа
    is_success: bool     # status_code < 400
    start_time: float    # Unix timestamp старта
    end_time: float      # Unix timestamp окончания
    error_msg: str | None = None
```

Вычисляемые метрики:
1. **Количественные:** общее число запросов, успешных, неуспешных, RPS (запросов в секунду), Error Rate %.
2. **Временные (Latency Distribution):**
   - Минимум ($min$)
   - Среднее арифметическое ($mean$)
   - Медиана ($p_{50}$)
   - 90-й процентиль ($p_{90}$)
   - 95-й процентиль ($p_{95}$)
   - 99-й процентиль ($p_{99}$)
   - Максимум ($max$)
   - Стандартное отклонение ($\sigma$)
3. **Группировка:**
   - По каждому отдельному эндпоинту
   - По категории (интерактивные пользовательские операции vs аналитические отчёты)
   - Агрегированно по всей системе
4. **Критерий соответствия SLA (R18/R19):**
   - $p_{95} \le 1000$ мс для интерактивных операций.
   - Число одновременно строящихся отчётов $\ge 10$ на протяжении тестового окна.
   - Error Rate $\le 0.0\%$.

## 5. Спецификация протокола испытаний (`docs/benchmarks/load-test-report.md`)

Генерируемый отчёт должен соответствовать строгой структуре, зафиксированной в ТЗ и критериях AC23/AC24.

### 5.1. Структура документа

```markdown

## 1. Паспорт испытаний и окружение
- Дата и время проведения
- Версия CRM и Git commit hash
```
